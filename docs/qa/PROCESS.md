# QA — процесс тестирования Voice Input Helper

Документ описывает, как проверять изменения расширения в процессе разработки и как оформлять отчёты о тестировании. Адаптировано из практики `myna-quick-input` (QT-подход), с учётом особенностей этого проекта.

## 1. Быстрая итерация без перезапуска основной сессии (devkit)

> **Важно (подтверждено на практике):** логи, которые интересуют при отладке расширения, попадают **только** в devkit-сессию (в терминал, где запущен `./run-gnome-shell-devkit.sh`). Логи основной сессии (`journalctl ... /usr/bin/gnome-shell`) ошибки расширения НЕ содержат — смотреть там бессмысленно.

Запуск devkit с сохранением полного лога и фильтрацией по расширению:

```bash
./run-gnome-shell-devkit.sh
# эквивалентно:
dbus-run-session -- gnome-shell --devkit 2>&1 | tee .tmp/devkit.log | grep -iE 'voice-input-helper|diserere\.github\.com|JS ERROR'
```

- Полный лог — в `.tmp/devkit.log` (папка `.tmp/` в `.gitignore`; оставлять после прогонов для последующего анализа).
- Отфильтрованная выборка (по расширению/ошибкам) — на экран; её стоит вставлять в отчёт (см. раздел 2, «Логи тестового прогона»).

Ключевые строки, которые сигнализируют о проблеме с расширением:
- `JS ERROR: ...` — исключение в коде (ниже в стеке указывается файл и строка `extension.js`);
- `Disabling extension ... (error: ...)`, `Failed to load` — расширение отключилось автоматически из-за ошибки.

### Включение расширения внутри devkit-сессии

`dbus-run-session` создаёт **изолированную шину D-Bus** — команды `gnome-extensions ...` из терминала основной сессии уходят в основную сессию, а не во вложенную. Поэтому расширение включается **внутри самой devkit-сессии** — это надёжный, проверенный путь:

- **приложение «Расширения» (Gnome Extensions)** внутри devkit-окна (панель → приложения, или через `gnome-extensions app` в консоли devkit-сессии) — кнопка-переключатель напротив «Voice Input Helper»;
- либо команда `gnome-extensions enable/disable voice-input-helper@diserere.github.com`, запущенная **в терминале самой devkit-сессии** (не в основной).

Вариация через `WAYLAND_DISPLAY=wayland-1 ...` из отдельного терминала — не рекомендуется (избыточна и ненадёжна).

### Проверка, что изменение подхватилось

1. Внести правку в код (`extension.js`, `metadata.json`, `stylesheet.css` и т.д.).
2. Вписать хэш коммита в `description`: `./set-qa-version.sh` (см. раздел 5). Это и есть метка версии для проверки.
3. В devkit-сессии **выключить** расширение и **включить** снова (кнопкой в Gnome Extensions).
4. Убедиться, что загружена нужная версия: внутри devkit-сессии выполнить `gnome-extensions info voice-input-helper@diserere.github.com` и сверить `description` — там должен быть свежий `(build <short-hash>)`. Если хэша нет или он старый — Shell загрузил закэшированную версию (код не перечитался).

**Подтверждено:** devkit перечитывает код с диска при каждом включении — без перезапуска сессии. В основной сессии это НЕ работает (код/метаданные кэшируются Shell при старте; сброс — только через полный logout/login).

### QA-хук длинного текста

Для проверки автопереноса в devkit (где нет IBus и неудобно вставлять большой текст мышью) в прототипе есть QA-хук, активируемый переменной окружения:

```bash
dbus-run-session -- env VHI_QA_TEXT=1 gnome-shell --devkit 2>&1 | tee .tmp/devkit.log | grep -iE 'voice-input-helper|diserere\.github\.com|JS ERROR'
```

При первом открытии окна в поле подставляется длинный текст (300–400 знаков) — удобно проверять перенос строк.

## 2. Чек-лист и шаблон отчёта о тестировании (чек-лист v1)

Единый источник чек-листа — [CHECKLIST.md](CHECKLIST.md). Он используется двояко:
- как **список проверок** текущего функционала (требования US-1…US-6 из REQUIREMENTS.md);
- как **шаблон отчёта**: при тестировании итерации копируется в отчёт, галочки проставляются, комментарии дописываются, отчёт сохраняется как артефакт итерации.

Формат: `- [ ]` / `- [x]` (Markdown-чекбоксы).

Шапка отчёта (см. [reports/ITERATION-01.md](reports/ITERATION-01.md)):

```markdown
# Отчёт о тестировании — итерация <N>: <краткое название>

Дата: <Время генерации отчета в формате YYYY-MM-DD HH:MM:SS>
Среда: GNOME Shell <версия>, <сессия: основная / devkit>
Расширение: voice-input-helper@diserere.github.com
```

> Версия, на которой проводилось тестирование, определяется коммитом, в котором лежит отчёт — отдельное поле «Коммит» не нужно.

### Логи тестового прогона (devkit-сессия)

Журнал: `dbus-run-session -- gnome-shell --devkit 2>&1 | tee .tmp/devkit.log | grep -iE 'voice-input-helper|diserere\.github\.com|JS ERROR'` (полный лог — `.tmp/devkit.log`).

```log

```

## 3. Строгий порядок коммитов: отчёт в одном коммите с протестированным кодом

> **Принцип (важен для отслеживаемости разработки):** коммит = протестированное состояние + заполненный отчёт **одним коммитом**. Это гарантирует, что каждый коммит отражает «ровно этот код прошёл ровно эти проверки», а история изменений сохраняет направление мысли (что правилось, что находилось при тестировании).

**Важно про PR:** pull request — **один на всю ветку, в конце**. PR открывается **один раз по завершении ветки**, когда изменения работоспособны и все тесты пройдены успешно (итоговый PR). Промежуточные состояния — в т.ч. с блокирующими дефектами — коммитятся на ветку **по строгому процессу (код + отчёт)**, но **не** в отдельные PR: на каждую итерацию/мелкую правку PR не создаётся. Отдельный PR оправдан только для ветки, признанной завершённой (например, чисто документационной), — тогда она проходит полный цикл «коммит + отчёт + итоговый PR».

### Последовательность (для любой итерации, в т.ч. в другой сессии)

**Один отчёт на всю ветку** — живой документ, который ведётся вдоль ветки и **обновляется** на каждом тестировании (не создаётся заново на каждую итерацию). Имя отчёта привязывается к этапу разработки и фиче: `docs/qa/reports/<версия>-<фича>.md`, например текущий MVP — `docs/qa/reports/v0-multiline-input.md`.

1. **Разработка** — правки кода/документации в рабочем дереве, **без коммитов** (желательно: отдельная ветка).
2. **Сгенерировать пустой шаблон отчёта** из чек-листа (копия с пустыми чекбоксами + шапкой «Дата/Среда», без поля «Тестировал»), сохранить под именем из правила выше (`<версия>-<фича>.md`).
3. **Тестирование** — пользователь заполняет чек-лист в отчёте по сценариям выше (галочки, дефекты, логи, заключение).
4. **Дефекты не правятся до коммита**: найденные дефекты (в т.ч. блокирующие) фиксируются в отчёте, и отчёт коммитится вместе с кодом **как есть**. Правки по результатам тестирования — только в **следующий** коммит, вместе с обновлением отчёта.
5. **Коммит — сразу после теста**: как только тестировщик сообщил, что тест проведён и отчёт заполнен, изменения + заполненный отчёт коммитятся одним коммитом. Версия, на которой тестировалось, однозначно определяется этим коммитом (hash в отчёте указывать не нужно). **После этого** — анализ тестовых данных и (если обнаружены дефекты) их исправление, уже в следующей итерации.
6. **Следующая итерация** — тот же отчёт **обновляется**, а не сбрасывается: исправленные дефекты отмечаются (галочка снимается с исправленного), остальные зафиксированные — остаются, обновляются логи/дата/заключение. Затем снова коммит «изменения + обновлённый отчёт» сразу после теста.

### Раздел «Что изменилось (история)» в отчёте

В отчёт (сразу после шапки) включается **раздел «Что изменилось (история)»** — журнал изменений по прогонам. Правила ведения:

- каждая **запись = одна итерация (снапшот)**: дата + краткая подпись (`### 2026-10-27 — итерация 2: фикс блокирующего дефекта (ожидает повторного тестирования)`);
- внутри записи — что изменилось с прошлого прогона (правки кода/документации) и статус («ожидает повторного тестирования», «закрыто» и т.п.);
- записи идут **последовательно, сверху вниз**: сверху — самая ранняя, снизу — самая свежая (в порядке прогонов);
- цель — видеть эволюцию состояния прямо из отчёта, не перелистывая историю коммитов.

> **Разделение ролей при ведении отчёта.** **Данные тестирования** (галочки чек-листа, комментарии, найденные дефекты, логи, заключение) вносит **пользователь/тестировщик** после каждого прогона. Раздел **«Что изменилось (история)»** — техническую сводку правок (что реально изменилось в коде/документации между прогонами и с каким статусом) — дополняет **агент** (например, при коммите «изменения + отчёт»). Агент НЕ заполняет и не меняет данные тестирования и не переписывает чек-лист/заключение по своему усмотрению.

По явной договорённости (ручная корректировка человеком) — тривиальные правки, для которых отчёт не несёт смысла: например, смена версии в `metadata.json`, правка `.gitignore`. В таких случаях отчёт не обязателен. Решение — всегда за пользователем.

### Как попросить агента (Claude Code)

При тестировании итерации можно попросить агента:
- сгенерировать **пустой шаблон** отчёта из чек-листа (копия с пустыми чекбоксами + шапкой «Дата/Среда», без поля «Тестировал»), сохранив под именем `<версия>-<фича>.md` (один на ветку), следуя последовательности выше (собрать изменения → сгенерировать отчёт → тест → коммит изменений+отчёта одним коммитом);
- после ваших правок (галочки + комментарии) — сверить с чек-листом и закоммитить изменения + заполненный отчёт одним коммитом; на последующих итерациях отчёт **обновляется** (не сбрасывается), как в пункте 6.

## 4. Особенности: диктовка Myna в devkit непроверяема

В devkit-сессии **нет IBus/input-method моста** — диктовку Myna (US-2) там проверить нельзя. Пункт чек-листа «Диктовка Myna» в devkit-отчёте помечается как **«требует проверки в основной сессии»** и НЕ считается дефектом/блокером. Проверка с реальной Myna — в основной сессии (после logout/login) либо в виртуальной машине.

## 5. Верификация версии кода при тестировании (вне devkit) и версионирование

### Временная пометка версии (хэш в `description`)

Расширение **кэшируется Shell при старте сессии** — в основной сессии (не devkit) код/метаданные не перечитываются до logout/login. Чтобы при тестировании на хосте/в VM понять, какая версия кода фактически загружена, в `description` в `metadata.json` вписывается короткий хэш коммита (виден в GUI «Расширения» и в `gnome-extensions info`):

```bash
./set-qa-version.sh          # вписать "(build <hash>)" в description
./set-qa-version.sh --clean  # убрать пометку (перед коммитом итерации)
```

- Хэш берётся из текущего `HEAD` (`git rev-parse --short HEAD`) — верифицирует «от какой базы собрано» (незакоммиченные правки не учитываются, но для ловли кэша этого достаточно).
- **Пометку снимать перед коммитом итерации**, чтобы она не попадала в историю/мастер.
- Скрипт `version` не трогает (там отдельное правило, ниже).

### Правило версии (semver) при завершении ветки

Версия в `metadata.json` (`version`) инкрементируется при завершении ветки:

- новый функционал (feat) → `MINOR`: `0.1.0 → 0.2.0`;
- багфикс/мелкие правки (fix) → `PATCH`;
- чисто документационные ветки (docs) → без инкремента;
- `1.0.0` — при стабилизации функционала.

Инкремент делается в момент завершения ветки (перед PR/мержем), отдельным коммитом или в коммите итерации.
